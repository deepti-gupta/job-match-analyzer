💼 Interview Questions You Can Now Answer

"Explain RAG in one sentence."
Retrieve the most relevant facts from your own data and inject them into the LLM prompt so it generates grounded answers instead of hallucinating.
"Why not send the whole document to the LLM?"
Context windows have limits, every token costs money, and irrelevant content degrades output quality. Chunking + retrieval sends only the most relevant 10%.
"What embedding model and why?"
all-MiniLM-L6-v2 via @xenova/transformers — runs ONNX in Node, no API key, 23MB, 384-dim. Fast for real-time use, accurate for semantic matching.
"Fine-tuning vs RAG — when to use which?"
Fine-tuning bakes knowledge into weights — expensive, slow to update. RAG retrieves at runtime — instant updates, no training. RAG for dynamic/private data.
"How do you measure if RAG is working?"
Inspect similarity scores in the RAG debug panel. Use RAGAS framework for automated evaluation: faithfulness, answer relevance, context precision.
"How would you scale this to production?"
Replace in-memory store with Upstash Redis Vector. Add streaming. Add user auth with vector namespaces. Evaluate with RAGAS on model updates.

Below: technical reference for the project code

What is RAG?

RAG = Retrieval-Augmented Generation. Instead of asking an LLM a question from its training data alone, you first retrieve relevant facts from your own knowledge base and inject them into the prompt. The LLM then generates an answer that is grounded in your data — not hallucinated from general knowledge.
❌ Without RAG
Ask LLM: "Does this candidate match the JD?" → LLM has no idea who the candidate is → generic or hallucinated answer.
✅ With RAG
Retrieve the candidate's real skills & experience → inject into prompt → LLM generates a grounded, accurate match score.

The 3-Phase Pipeline

📥 Phase 1 — Ingest (one-time)
  • Load resume — JSON profile or uploaded PDF/text
  • Split into semantic chunks (summary, skills, each job = 1 chunk)
  • Call embed(chunk) → @xenova/transformers runs all-MiniLM-L6-v2 locally → returns a 384-dimensional float vector
  • Store { id, text, embedding[], metadata } in the in-memory vector store

File: src/lib/ingest.ts · Runs when first analyze call arrives (lazy) or on upload

↓
🔍 Phase 2 — Retrieve (per request)
  • User pastes a job description (JD)
  • Call embed(JD) → same model produces a 384-dim vector for the JD
  • Compute cosine similarity between JD vector and every stored resume chunk vector
  • Return the top-4 most similar chunks — visible in the RAG Debug Panel

Files: src/lib/retriever.ts · src/lib/vectorStore.ts

↓
🤖 Phase 3 — Generate (per request)
  • Build an augmented prompt = retrieved chunks + full JD + instructions
  • Call Groq API with model qwen/qwen3.8-27b in JSON mode
  • LLM returns structured JSON: matchScore, matchSummary, matchedSkills, missingSkills, strengthPoints, coverLetter, keywordSuggestions
  • Parse & validate the JSON → send to frontend

File: src/lib/analyzer.ts

What is an Embedding?

An embedding is a list of numbers (a vector) that captures the meaning of text. Similar meaning → similar numbers → high cosine similarity. This is how "React expert" and "strong React skills required" score high together even though the exact words differ.
// "React TypeScript expert" → embed() →
[ -0.075, -0.031, 0.044, 0.112, -0.089, ... ] ← 384 numbers

// "frontend developer React TypeScript 5 years" → embed() →
[ -0.068, -0.028, 0.051, 0.108, -0.091, ... ] ← 384 numbers

// Cosine similarity between them:
similarity = 0.8269 ← very high → correctly identified as related!

// "Python data science machine learning" → embed() →
[ 0.031, 0.091, -0.103, -0.044, 0.172, ... ]
similarity = 0.21 ← low → correctly identified as unrelated to React

Cosine Similarity — The Math

// Formula: similarity(A, B) = (A · B) / (|A| × |B|)

// Dot product: multiply each pair of numbers, sum them up
dotProduct(A, B) = A[0]×B[0] + A[1]×B[1] + ... + A[383]×B[383]

// Magnitude: "length" of the vector
magnitude(A) = √(A[0]² + A[1]² + ... + A[383]²)

// Result: 0 = completely unrelated, 1 = identical meaning
cosineSimilarity = dotProduct / (magnitude(A) × magnitude(B))

This is exactly what vectorStore.ts computes — no library, just arithmetic.

Request Lifecycle — Step by Step

  • User pastes a JD → clicks Analyze Match → POST /api/analyze called with { jobDescription }
  • storeSize() === 0 → auto-calls ingestResume() → 6 chunks created, each embedded via ONNX → stored in store[]
  • retrieveRelevantChunks(jd, 4) → JD embedded → cosine similarity vs all chunks → top-4 returned with scores → shown in RAG Debug Panel
  • buildPrompt(chunks, jd) → context block + full JD + JSON schema including keywordSuggestions field
  • Groq API call: model: "qwen/qwen3.8-27b", response_format: json_object, temperature: 0.3
  • JSON parsed → validated → returned: matchScore, skills, strengths, coverLetter, keywordSuggestions[]
  • Frontend renders: score gauge → skill gaps → ATS keywords → cover letter → RAG debug panel

Prompt Engineering — Why It's Structured This Way

JSON mode (response_format)
Forces the LLM to output only valid JSON. Without this, models sometimes wrap JSON in markdown fences (```json ... ```) which breaks JSON.parse(). The fallback regex /\{[\s\S]*\}/ handles edge cases.
temperature: 0.3
Lower temperature = more deterministic output. For scoring and skill matching you want consistency, not creativity. Cover letter generation still benefits from slight variation.
Context injection
The retrieved chunks are labelled: [Section 1 — skills], [Section 2 — experience]. This helps the LLM understand the structure of the information it's reading.
ATS specialist persona
Prompt begins: "You are an expert career coach, recruiter, and ATS specialist." This activates the model's knowledge of how ATS systems score keywords — critical for the keyword suggestions feature.

Fix: auto-ingest inside /api/analyze when storeSize() === 0.

⚠️
Groq model deprecation — llama-3.1-8b-instant removed. llama3-8b-8192, gemma2-9b-it, mixtral all deprecated too.
Fix: switched to qwen/qwen3.8-27b (available, supports JSON mode).
⚠️
pdf-parse@2.x breaking change — v2 changed from module.exports = fn to an ESM module, requires Node 20.16+, completely different API.
Fix: pinned to pdf-parse@1.1.1. Runtime guard: typeof pdfParse === "function" ? pdfParse : pdfParse.default.
⚠️
onnxruntime-node webpack error — Next.js webpack tried to bundle native .node binary files, which is impossible.
Fix: added onnxruntime-node to serverComponentsExternalPackages and webpack externals in next.config.js.
⚠️
"bad XRef entry" on PDF upload — pdfjs-dist throws this for PDFs with malformed cross-reference tables. Very common with Word exports, Canva resumes, and online resume builders.
Fix: 3-layer fallback in extractPdfText() — attempt 1: { max:0 } recovery mode · attempt 2: { version:"v1.10.100" } older parser · attempt 3: friendly error telling user to paste text.

Self-Test Questions

Q1. Why do we chunk the resume instead of sending the whole thing to the LLM?
LLMs have context limits and cost money per token. Chunking lets us retrieve only the most relevant parts (e.g., for a React JD, retrieve skills + React experience chunks) instead of sending everything. This is more accurate and cheaper.
Q2. Why must the JD and resume chunks use the same embedding model?
Embeddings are only comparable within the same model's vector space. Mixing models is like measuring one distance in miles and another in kilometres — the cosine similarity numbers would be meaningless.
Q3. What does cosine similarity measure, and what's its range?
It measures the angle between two vectors — how similar their direction is, independent of their length. Range: 0 (unrelated) to 1 (identical meaning). Two texts can have very different word counts but high similarity if they mean the same thing.
Q4. What is "augmented" in Retrieval-Augmented Generation?
The prompt is augmented (enriched) with retrieved context before being sent to the LLM. Instead of just "analyze this JD", the prompt becomes "here are the candidate's actual skills and experience [retrieved chunks] — now analyze this JD". The LLM generates from facts, not from guessing.
Q5. Why does the vector store reset on Vercel cold starts, and how is it handled?
Vercel serverless functions are stateless — memory is wiped when the container shuts down. The store is re-populated on the next /api/analyze call via auto-ingest (storeSize() === 0 check). For production, a persistent store like Upstash Redis would be used instead.
Q6. What is the RAG Debug Panel showing, and why is it useful?
It shows the top-4 resume chunks retrieved for the current JD — their section label (skills/experience), similarity score, and a text preview. It makes Phase 2 (retrieval) transparent: you can see exactly which resume content was injected into the LLM prompt, and why a high or low match score was given.
Q7. Why does the keyword suggestion prompt say "only suggest keywords the candidate can authentically add"?
Without this rule, the LLM would list every keyword in the JD — including skills the candidate doesn't have. The rule keeps suggestions grounded in the actual resume content, so the candidate can back them up in an interview. This is the same RAG principle: context constrains generation.

Next Steps to Go Deeper

🔁 Streaming responses
Use groq.chat.completions.create({ stream: true }) + Next.js ReadableStream to show the cover letter being typed in real time.
💾 Persistent vector store
Replace in-memory array with Upstash Redis Vector. Vectors survive cold starts. Add a user ID so multiple people can have their own resume indexed.
📊 Better chunking
Use sliding-window chunking with overlap (e.g. 512 tokens, 50 overlap). Preserves context at chunk boundaries. Try langchain's RecursiveCharacterTextSplitter.
🎯 Re-ranking
After retrieval, use a cross-encoder model (not bi-encoder) to re-rank the top-K chunks. More accurate than cosine similarity alone for complex queries.
